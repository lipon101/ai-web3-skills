# Argus — Rust-first submission-grade audit pipeline

Argus is a **single staged pipeline**, not a bag of prompts. Findings move forward through 13 ordered stages (plus optional Stage 9 for fix verification). Each stage either advances, downgrades, or kills a finding. The final stage emits only what survived every gate.

`$SKILL_DIR` = the directory containing this `SKILL.md`. Resolve from where this file was loaded.

## When to use

Use Argus when the user asks to audit a Rust codebase end-to-end and wants submission-grade output (bug bounty, audit contest, security report). Argus is **Rust-first** — Solana programs, CosmWasm contracts, Substrate pallets, generic Rust services. If the target is Solidity / Move / Vyper, do not use Argus; the audit stage assumes Rust semantics.

Argus replaces manually chaining: protocol-mapping skill → audit skill → PoC building → judge skill → platform validator → bounty triage → duplicate check.

**Optional Stage 9 — fix verification**: when the user has applied a fix for a previously-found vulnerability and wants to verify it before merging, Argus runs a 5-phase fix-check (root-cause coverage, completeness, regressions, smart-contract-specific, verdict).

## Operating principles

1. **Pipeline over prompt soup.** Every stage has a defined input, a defined output file, and a verdict that decides the finding's fate. Later stages depend on earlier ones — never reorder.
2. **Evidence over hype.** No claim survives without a code citation, a passing PoC, or a verifiable doc reference. "Probably" is not evidence.
3. **Kill weak findings early.** A finding without a strong PoC dies in Stage 3. A finding that fails adversarial review dies in Stage 4. Every stage is allowed to drop the count.
4. **Skepticism over optimism.** Default to challenging findings, not celebrating them. Borderline cases tip toward `REFINE` or `DISCARD`, never auto-`SUBMIT`.
5. **Project-aware finalization.** The last gates apply the *live* bounty page (Stage 6) and the *target project's GitHub repo* (Stage 7). Generic bug-bounty advice is rejected.
6. **Severity is independent.** Stage 4's Pass D re-grades severity from the verified attack path, not from the claimed severity. Argus can upgrade as well as downgrade.
7. **One coherent skill.** Do not invoke this skill recursively. Subagents are for parallel sub-work *inside* a stage (up to 12 audit angles in Stage 2; per-finding adversarial drafts in Stage 4 / 7).
8. **(infra mode, NEW v0.3.3) Live E2E evidence over tool-confirmation alone.** Stage 3 CONFIRMED for `infra` mode requires a Tier-1-live-e2e artifact — a runnable test that reproduces the bug against the actual codebase's code path, not just a deterministic-backend tool match. `cargo audit` alone, Miri alone, Kani alone are necessary but not sufficient — every infra-mode CONFIRMED finding needs a live reproducer saved to `$RUN_DIR/3-verification/F-NN/e2e/`. See `references/e2e-test-discipline.md` for per-component-type E2E patterns. **The F-07 over-claim (cargo-audit-CONFIRMED, codebase-UNREACHABLE) was the failure that established this rule.**
9. **(infra mode, NEW v0.3.3) REFINE findings auto-loop.** When Stage 6/7/8 produces a finding in REFINE with a "needs X verification" rationale, the orchestrator auto-invokes a refinement sub-stage that builds the X verification harness, runs it, and updates the verdict (SUBMIT if reproduced / DISCARD if refuted / stay REFINE only if test result is genuinely ambiguous). Manual review of every REFINE finding is no longer the default — the pipeline attempts the refinement itself. See `references/refine-loop.md`.

## ⚠️ AI-generated content provenance — read this BEFORE submission

Argus is AI tooling. Findings produced by Argus pipelines are AI-generated by definition.

**Cantina explicitly bans unverified AI-generated findings** (Cantina AI-3) and enforces detection aggressively — submission without manual validation results in INVALID + ban. Other platforms increasingly apply similar discipline.

Before submitting any Argus finding to **any** platform — especially Cantina, but in practice all of them:

1. **Manually re-read the cited code at the cited line numbers.** Do not trust subagent or Argus output verbatim.
2. **Independently re-derive the exploit path from first principles.** Confirm the chain of reasoning yourself.
3. **Run the PoC.** Read the output. Confirm it matches the verdict.md claim.
4. **Re-verify impact against the program's specific scope** (not Argus's generic analysis).
5. **Re-write the writeup in your own words.** Do not paste Argus output verbatim.

Stage 5 includes an explicit `manual-validation-acknowledgment` field. When the platform target is Cantina (BB or Competition), Stage 5 will refuse to ADVANCE without the user confirming acknowledgment. For other platforms, the gate is a strong recommendation surfaced in Stage 8 output.

```
[3]   PoC Generation (GATE)     →  $RUN_DIR/3-poc/F-NN/{poc.*, repro.md, verdict.md}

[4.5] Combination Attack        →  $RUN_DIR/4-5-combination/{F-AB-NN.md, _pairs-summary.md}
[5]   Platform Validation       →  $RUN_DIR/5-platform/F-NN.md  (rubric scorecard + longest-fund-loss-chain framing v0.2.0)
[6]   Program Triage            →  $RUN_DIR/6-program/{bounty-page.md, extended-scope.md, F-NN.md}
[7]   Duplication Triage        →  $RUN_DIR/7-duplication/F-NN.md (+ adjacent-hit rescan)
[8]   Final Output              →  $RUN_DIR/8-final/{submission-grade.md, refine.md, discard.md, submission-formatted/, _polish-summary.md}
[9]   Fix Verification (OPT)    →  $RUN_DIR/9-fix-verification/F-NN.md

ITERATE feedback arc: Stage 4 instructive-KILL → re-dispatch single angle on cited region → new candidate at Stage 3.
```

**`$RUN_DIR`** = `<project-root>/argus/<UTC-timestamp>/`. One run per invocation. Never overwrite a prior run.

**Finding ID** = `F-01`, `F-02`, … assigned in Stage 2 and carried through every later stage. The ID never changes.

**Verdict buckets** (final, set in Stage 8):
- `SUBMIT` — passed every gate; ready to file (after manual validation per the AI-provenance rule above).
- `REFINE` — real issue, but missing PoC strength / scope clarity / dup confirmation. Fix before submitting.
- `DISCARD` — failed a gate that cannot be repaired (out of scope, design intent, hard duplicate, refuted).

## Audit mode (NEW v0.3.0)

Argus supports two distinct audit missions. Read `references/audit-modes.md` at Stage 0 start to determine which mode applies.

- **`smart-contract` mode** (legacy default). Solana Anchor programs, CosmWasm contracts, Substrate pallets, on-chain Rust applications. Targets logic-layer bugs (oracle manipulation, replay, scope carve-outs, account substitution, CPI re-entry, threshold math, governance flaws). The Stage 2 angles + V1-V132 attack vector library + Code4rena / Sherlock / Cantina platform criteria all live here.
- **`infra` mode** (NEW v0.3.0) — **the user's primary mission**: DLT infrastructure (validator clients, consensus engines, p2p networking, crypto libraries, ZK proof circuits, storage engines, RPC nodes, off-chain workers, bridge relayers, wallet libraries, smart-contract VMs). Targets systems-Rust bugs (UB / aliasing / memory safety, unsafe trait soundness, integer overflow, concurrency, cryptographic misuse, resource exhaustion, FFI safety, supply-chain CVE) **+ ZK circuit soundness (v0.6.1 — under-constrained witness cells, missing range/boolean checks, custom gate incompleteness, lookup argument gaps)**. Uses **deterministic verification backends** (Miri / Kani / Loom / Rudra / cargo-fuzz / cargo-audit / cargo-deny / cargo-geiger / Clippy security-lints / MockProver) at Stage 3 with the LLM only for hypothesis generation + harness writing + orchestration. Severity is **Impact × Reachability matrix** (deterministic 3×6 lookup), not English rubric. Stage 4 Pass A/B/C/D adversarial review is **SKIPPED** in infra mode — the tool's verdict IS the gate.

Mode is selected at Stage 0 via AskUserQuestion. The **"Recommended" sticker** on the prompt MUST follow the priority order in `references/audit-modes.md` §"Recommendation discipline":

1. **Bounty page category tag** (highest priority). Parse the Immunefi / HackenProof / vendor bounty page's category selector. `Blockchain/DLT` / `Infrastructure` / `Node` / `Wallet` / `Library` → recommend `infra`. `Smart Contract` / `DeFi` / `NFT` / `AMM/DEX` / `Lending` / `Bridge (contract-side)` → recommend `smart-contract`. **Immunefi presence alone is NOT a smart-contract signal** — Immunefi hosts both kinds; the category tag distinguishes.
2. **Crate-name / repo-shape heuristics**. Crate names matching `*-runtime`, `*-validator`, `*-node`, `*-consensus`, `*-wallet`, `*-crypto`, `*-monero-*`, `*-substrate-*`, `*-cosmos-sdk-*`, `cometbft-*`, `solana-runtime`, etc. → `infra`. README mentioning "Anchor program", "CosmWasm contract", "Substrate pallet" → `smart-contract`.
3. **Project-shape default** per `enumerate.sh` output. `anchor` / `cosmwasm` → `smart-contract`. `generic-rust` → `infra`. `substrate` / `solana-native` / `unknown` → mandatory user confirmation.
4. **Prior-run history** (lowest priority; only pro-signal when prior SUBMIT findings were independently validated). **Prior runs that produced INVALID / SC-2 / out-of-scope findings are ANTI-signal** — the prior runs were themselves miscategorized; recommend the OTHER mode.

Every downstream stage routes per `references/audit-modes.md`. Stages 0, 1, 2, 3, 4, 5, 6, 8, 9 have mode-specific references. Stage 7 (duplication), the FINDING schema fields (`weaponization_check`, `reachability_check`, `code_comment_scan`, etc.), and pipeline cross-stage invariants are mode-independent.

**Canonical case** (per `audit-modes.md`): **monero-oxide** — `generic-rust` shape + Immunefi Blockchain/DLT tag + prior SC-mode run produced INVALID finding (v0.2.5 F-15 `Decoys::select_n`, the failure that drove this entire v0.3.0 pivot). All three signals point at `infra`. Recommendation MUST be `infra`.

## Inputs Argus expects

Argus is autonomous once invoked, but it asks the user up front for:

- **target path** (default = cwd) — Rust project root
- **target program / bounty URL** (Stage 6 source of truth — Immunefi / HackenProof / Cantina / Sherlock / Code4rena page, or self-hosted scope file). If absent, `program-mode = generic` and Stage 6 applies platform-default rules but flags missing source.
- **target project GitHub repo URL** (Stage 7). If absent, `dup-mode = local-only` and Stage 7 explicitly flags reduced confidence.
- **manual-validation acknowledgment** (Stage 5 — required for Cantina targets). Argus prompts at the start of Stage 5 if the platform is Cantina.

Use `AskUserQuestion` once at the start of Stage 1 to collect the bounty URL and the GitHub repo URL together. Do not re-ask later (except the Cantina manual-validation acknowledgment at Stage 5 start).

## Stage execution order — what to do, in order

For each stage, follow the full contract in `references/pipeline-overview.md`. Condensed cycle:

1. **Start stage** → set the matching todo to `in_progress`, read the matching reference file(s) from the table above, create the stage's output subdirectory.
2. **Execute stage** → operate only on the prior stage's output artifacts and the project source. Do not re-derive earlier-stage data; trust your own files.
3. **Verdict every finding** → write per-finding output file with explicit `STATUS: ADVANCE | DOWNGRADE(severity) | KILL(reason)`. KILL'd findings stop here — later stages skip them.
4. **End stage** → mark todo `completed`. Print one-line summary: `Stage N: X advanced, Y downgraded, Z killed.`

## What Argus must NOT do

- Do not skip the PoC stage. A finding without a PoC verdict file does not advance.
- Do not skip Stage 4's Pass D severity calibration — claimed severity is not the ceiling.
- Do not skip the live bounty-page fetch in Stage 6. If WebFetch fails, retry once, then surface the failure to the user — do not fabricate scope.
- Do not skip the GitHub duplication probe in Stage 7 when the user supplied a repo URL.
- Do not output volume. The Stage 8 final list is allowed to be empty if nothing survived. An empty `SUBMIT` bucket is a successful run.
- Do not let Stage 2 act like a Solidity scanner with Rust labels. Stage 2 is governed by `rust-audit-guidance.md` and `rust-protocol-types.md`, which catalogue *Rust* failure modes and Rust-ecosystem protocol-type threats.
- Do not paraphrase the source repos this skill was built from. Stage logic is the contract; the source repos are gone from this skill once it ships.
- Do not promote a finding past a stage just because effort was invested. The cost of misclassification dominates.
- Do not present Argus output as a finished submission. Per the AI-provenance rule, manual validation is the user's responsibility.

## 0. Calibration headline (read first)

The single most important empirical fact (SoK: Chaliasos et al., USENIX Security 2024, n=141 SNARK vulns): **circuit-layer bugs are 70% (99/141) of all SNARK vulnerabilities, and within the circuit layer 96% (95/99) are UNDER-CONSTRAINED**, almost all causing soundness breaks (95 soundness vs 4 completeness). Over-constraint is ~1%, computational ~3%. **"Missing constraint → counterfeiting" is the modal ZK bug by an enormous margin.** An auditor optimizing for one thing should optimize for *what binds this value?*

The second most important fact: **these bugs survive professional audits and pass MockProver + happy-path tests.** RISC Zero CVE-2025-52484 was found post-audit; SP1/Plonky3 FS bugs found by external teams after release; the OpenVM AUIPC bug is a single `skip(1).enumerate()` transposition that reads as correct. The code COMPILES, the honest prover produces VALID proofs, and tests PASS — the bug is the *absence* of a constraint, invisible to dynamic testing and to reading the honest path. Detection is overwhelmingly manual (SoK: 86 circuit bugs by audit, 10 by disclosure, 3 by trackers; automated SNARK tools used in only 5/75 audits). **Implication: the marginal value of a systematic assigned-vs-constrained enumeration is high, and the highest-signal confirmation is a mechanical forged-witness reproduction, not more reasoning.**

The third fact, added this pass: **soundness lives in two layers the angle must cover separately.** (a) IN-CIRCUIT under-constraint — the modal case (Orchard, Montgomery exceptional-case, AUIPC limb). (b) VERIFIER/SETUP-PARAMETER soundness in the surrounding Rust — Groth16 VK degeneracy (FOOM `delta2==gamma2`, ~$1.8M), trusted-setup element leak (Zcash CVE-2019-7167), unverified prover evaluations (dusk-plonk, ~$60M-class), missing point/subgroup/identity validation (Aztec "0 bug"). Argus audits Rust circuit code, so layer (a) is primary; layer (b) is the proving-system Rust this angle owns (NOT the black-box integration that Crypto Soundness owns) and was previously absent.

## 2. Per-class methodology

Each entry is a **discovery procedure that finds the bug without already knowing the answer**. Classes already fully covered by the angle (C1 base case, C4, C6) are summarized only where this dossier adds a sharper procedure; the genuinely uncovered classes get full treatment. Every procedure ends in a mechanical falsification step, because the empirical record (§0) shows reasoning-only review is exactly where these slip through.

### The unifying procedure — Uniqueness Constraint Propagation (UCP)

> This is the single procedure behind every firm's checklist (Picus/QED2, Veridise, zkSecurity, ToB). Run it first; the per-class procedures are specializations. **Grep is a seed-generation step, not the procedure** — §5 shows syntactic linting misses the highest-impact semantic binding gaps (Orchard is invisible to circomspect). The procedure is the forward-determination trace below; the framework grep tables in §3 only enumerate candidate cells to feed into it.

- **Signal**: any output or public signal of the circuit, and any intermediate that feeds an output.
- **Procedure**: Reframe the whole audit as one question — *"For fixed circuit inputs, is each output UNIQUELY determined by the constraints?"* Then run UCP by hand:
  1. Seed `K = {input/instance signals}` (known-determined).
  2. For each constraint, if it expresses a signal as a **function** (total) of signals already in `K` — `s = f(K)` — add `s` to `K`.
  3. Repeat to fixpoint `K'`.
  4. Any OUTPUT not in `K'` is a candidate under-constraint: it is bound only by **relations** (which admit ≥2 witnesses), not by a function.
  5. For each candidate, exhibit two witnesses `(w1, w2)` agreeing on inputs+outputs-so-far but differing on the candidate while satisfying ALL constraints. Success = CONFIRMED.
- **Mechanical evidence**: Picus/QED2 on R1CS/circom/gnark returns `safe` / `unsafe` (+ counterexample witness pair, exit code 9). For Halo2, quantstamp/halo2-analyzer (SMT). When no tool covers the framework (arkworks, bellman, plonky2/3) → build the two-witness PoC by hand (MockProver / `is_satisfied()` accepting a forged witness).
- **Anti-pattern**: **a signal appearing in many constraints is NOT necessarily determined** — `out·in===out` constrains a RELATIONSHIP, not a value. Conversely a signal bound by a single equality to an already-determined signal IS fully constrained even if it looks "lonely." Count function-determination, not constraint-count.
- **Source**: Pailoor et al., PLDI 2023 (QED2/Picus) §7; Veridise; SoK §0.

### C2 — Unconstrained gadget output (`out` never `=== 1`)

- **Signal**: every instantiation of a comparator/validator gadget whose security depends on its output (`LessThan.out`, `BigLessThan.out`, `IsZero.out`, `IsEqual.out`, EC-point validators, range proofs, returned `AssignedCell`).
- **Procedure**: For each instantiated gadget, find where its output is USED. (1) Is the output EQUATED to its required value (`=== 1`, `=== 0`, folded into a sum that is itself `===`'d, copied into a constrained instance)? (2) Or is it merely read into another signal? If only read, **the gadget is decorative — instantiating it is not the same as enforcing its verdict.** List each comparator/validator call; for each, locate the line that constrains its output; if absent, flag.
- **Mechanical evidence**: feed an input the gadget would reject (coord = field_prime; `a > b` for a `LessThan` meant to pass) and confirm the proof still verifies (golden: pubkey coord = modulus accepted, the circom-pairing repro).
- **Anti-pattern**: outputs used purely for witness branching (not security) need not be `=== 1`. An output constrained transitively (folded into a `===`'d sum) is sound. Distinguish "output IS the security check" from "output feeds a constrained selector."
- **Source**: Veridise circom-pairing; 0xPARC "Missing Output Check Constraints."

### C3 — Missing range / canonical constraint (with the two nuances the angle omits)

- **Signal**: any value the circuit TREATS as a bounded integer — array index, byte, bignum limb, shift amount, comparator operand, nullifier, anything crossing the EVM-256 / field-254 boundary.
- **Procedure**: For each such value state its INTENDED domain (n bits, < p, < divisor, in {0,1}). Then verify the *enforcing* constraint exists, applying the two nuances:
  1. **`Num2Bits ≠ range-check`** (canonicity): `Num2Bits(n)` only proves an n-bit decomposition exists; because the field is mod p, `p − k` also has an n-bit form. Demand `Num2Bits_strict` / `AliasCheck` / an explicit `< 2ⁿ` for a true bound. This nuance underlies ZkDrops, Nightfall, Dark Forest, Semaphore.
  2. **Limb-loop binding (re-derive, do not grep)**: for any decomposition `v = Σ limbᵢ·RADIXⁱ`, you must prove the recomposed value is UNIQUELY represented and stays below both the target width and the native field modulus. Do it in three independent steps, none of which depends on recognizing a specific iterator idiom:
     (a) **Index-domain re-derivation**: for the loop that installs a per-limb check, write down by hand the index sequence the iterator actually produces, ignoring variable names. If a selector keyed on `i == last` (the tight high-limb check) is never reached by that produced sequence, the most-significant limb falls through to the DEFAULT (full-width) check. (Any iterator transformation before `enumerate` — `skip`, `rev`, `filter`, `zip`, `windows` — shifts the index domain; re-derive rather than assume.)
     (b) **Residual-width binding**: independently compute the MSB limb's intended width = `TARGET_BITS − (NUM_LIMBS−1)·CELL_BITS`, and confirm the code installs a check of exactly that width on exactly that limb (often via a scale factor `2^(NUM_LIMBS·CELL_BITS − TARGET_BITS)` feeding a shared CELL_BITS lookup — verify the exponent is exact).
     (c) **Max-sum < modulus**: set every limb to its CHECKED maximum and compute `max_sum`; assert `max_sum < 2^TARGET_BITS` AND `max_sum < p`. If `max_sum` reaches `2^TARGET_BITS` or `p`, the decomposition admits an alias regardless of how clean each individual limb check looks. Range-checking every limb is NOT sufficient when their combined width exceeds `log2(p)` — small native fields (BabyBear ~31b, Mersenne31 ~31b, Goldilocks ~64b) have almost no slack.
- **Mechanical evidence**: assign the MSB limb a value inside the BUGGY bound but outside the intended residual bound (and likewise feed `x` vs `x+p` at the field boundary); show MockProver/`is_satisfied()` still accepts and the recomposed value mod p differs from the honest one. A missing constraint passes the HONEST-witness run, so only the out-of-range witness-substitution test is dispositive.
- **Anti-pattern**: when `TARGET_BITS == NUM_LIMBS·CELL_BITS` (no slack) a plain CELL_BITS check on every limb IS the correct binding — nothing to off-by-one. The tight bound may also be enforced elsewhere (a separate `assert_bits` on the top limb, a dedicated narrow lookup, a final `value < TARGET` / `< p` check); confirm NO other constraint binds the MSB residual and that `max_sum` actually reaches the bound before flagging. A value already produced by a constrained bit-decomposition upstream or covered by a lookup table is range-bound. **Regression note**: recently-patched range-check code is higher-risk — the OpenVM off-by-one was introduced by a typo in the FIX for an earlier overflow vuln; re-derive the bound from scratch, do not trust the patch.
- **Source**: 0xPARC #1/#2/#9/#18; OpenVM CVE-2025-46723 + first-party `auipc/core.rs` (verified); RareSkills AliasCheck; ICME small-fields background.

### C5 — Output not bound to public input / instance column

- **Signal** (Halo2): a circuit with `instance` columns where the final result cell is produced by `assign_advice` and there is NO `layouter.constrain_instance(cell, col, row)` / `assign_advice_from_instance` for it. Compiler "unused instance column" hints.
- **Procedure**: (1) List every instance column declared. (2) For each, find the call that ties an advice cell to it. (3) If an instance column has no tie, the public output is decoupled from the witness — the prover's result is not checked against the public statement. Follow copy/permutation chains: a value may be bound transitively (advice copied to a cell that IS `constrain_instance`'d).
- **Mechanical evidence**: MockProver run where the advice output differs from the instance value; if it still passes, the binding is missing (teddav `mul0`/`merkle0`).
- **Anti-pattern**: instance bound transitively through an aggregate (a single hash-of-all-inputs public input). Verify no aggregate commitment already covers it.
- **Source**: teddav/halo2-soundness-bugs; bellperson/rust-fil-proofs.

### C7 — Unconstrained inverse / division gadget

- **Signal**: any gadget named `*inverse*`/`*div*`/`mul_by_inverse`/`recip`, any native `.inverse()`/`.invert()`/`/` whose result is allocated as a witness, any `a = q·b + r` decomposition with witness q/r.
- **Procedure**: Enumerate every witnessed value claiming a mathematical property (inverse, sqrt, quotient, remainder). For each, locate the gate that ENFORCES the defining identity: `d·d_inv−1=0`, `r·r−val=0`, `q·b+r−a=0` AND `0≤r<b` AND `b≠0`. The degenerate case is the bug: `out<--a/b` with only `out·b===a` is satisfied by ANY `out` when `a=b=0` (`0===0`). For modulo, missing `r < divisor` lets an alternate `(q',r')` encode a false result (Polygon zkEVM divARITH: `10·9+11 = 101` passes with remainder 11 ≥ divisor 10).
- **Mechanical evidence**: assign the hint a wrong value (`d_inv=0`, a random element, `r'≥b`) and confirm `cs.is_satisfied()` / MockProver still accepts. Diff against the RUSTSEC-2021-0075 fix commit shape (the fix ADDS the product constraint).
- **Anti-pattern**: the relation may be enforced one hop DOWNSTREAM (the result is later multiplied by `d` and equated to the numerator) or the safe idiom routes through an `IsZero` gadget that forces uniqueness. Trace one hop before flagging.
- **Source**: RUSTSEC-2021-0075 / CVE-2021-38194 (verified); Veridise "Sharp rocks"; arkworks PR #70; 0xPARC Polygon zkEVM remainder.

### C8 — Host-assertion masquerading as a constraint

- **Signal**: `assert!`, `debug_assert!`, `panic!`, `assert_eq!`, `?`-returned `Result`, or any Rust/Go control-flow check inside a `synthesize` / witness-gen / hint function; circom `assert()`; a function named `*constrain*`/`*enforce*`/`*range_check*` whose body lacks a `cs.enforce`/`create_gate`/`connect`/`<==`/`AssertIsEqual`.
- **Procedure**: Grep the constraint-building code for host-language assertions and conditionals. For each, determine whether it ALSO emits a constraint. A check that only `assert!`s or only branches in the host runs during proving but is invisible to a prover who hand-crafts the witness; `debug_assert!` is doubly dangerous (compiled out in release). Flag any security check whose **sole** enforcement is a host assertion.
- **Mechanical evidence**: build in release mode (debug_asserts gone) OR bypass witness-gen and assign the value the assertion would reject; prove + verify. Acceptance proves the assertion was not a constraint.
- **Anti-pattern**: assertions on PUBLIC/config values at circuit-construction time (constrain circuit shape, not the witness) are fine; assertions that duplicate an existing real constraint (defense-in-depth) are not bugs.
- **Source**: ToB Axiom TOB-AXIOMv2-3 (verified pattern); 0xPARC #19 (Summa); ChainSecurity "Circom assertions: misconceptions and deceptions."

### C9 — Nondeterministic witness / non-unique output (double-spend frame)

- **Signal**: outputs derived from values with algebraic multiplicity (square roots, signatures, modular inverses, truncating hashes, non-canonical encodings) and identifiers meant to be unique (nullifiers, commitments, keys).
- **Procedure**: For each public output `O` claimed to uniquely identify a statement, derive the ambiguity FROM THE OPERATION, not from a memorized list: identify the algebraic operation that produced `O` and ask whether it is **injective under the constraints** — does the inverse relation admit >1 preimage? Concretely: for fixed public inputs, can a prover produce TWO distinct valid witnesses yielding `O`, or one witness yielding two distinct `O` for the "same" secret? An operation whose constraint is a non-injective relation (`r²=in` → ±r; `s·G` signature → malleable s; a truncating hash → high bits free; a non-canonical encoding → multiple representatives; an index not bit-bounded → wrap) is the source. If the application assumes uniqueness (double-spend prevention) but the producing operation is non-injective under the constraints, flag.
- **Mechanical evidence**: produce a second valid witness for the same statement (negative root, malleated signature, high-bit-mutated index) and show both proofs verify with DIFFERENT nullifiers → double-claim/double-spend.
- **Anti-pattern**: nondeterminism the application explicitly tolerates (a hint whose multiple solutions are all later constrained to one canonical value) is fine. Confirm the ambiguous value is actually consumed as a unique key before flagging.
- **Source**: 0xPARC #8 (StealthDrop), #6 (Aztec); teddav `sroot`.

### C10 — Compute-constrain semantic diff (TCCT)

- **Signal**: any place where witness-gen logic and constraints are written separately — circom `<--` RHS vs `===`; an if-then-else encoded as a product; a custom gate whose polynomial does not obviously equal the documented relation.
- **Procedure**: For each assigned signal, collect `S_compute` = the set of signals used in its witness computation, and `S_constrain` = the set of signals appearing in constraints involving it. **Diff the two sets.** If the constraint set OMITS an input the computation depended on, the relationship to that input is unconstrained: vary the omitted input while holding the assigned output fixed and confirm the constraints remain satisfiable (proof forgeable). Equivalently: write (a) what the witness generator computes and (b) what the constraint enforces, as two field predicates, and look for the gap — a branch the constraint doesn't cover, a product encoding with a spurious root, an else-branch value never pinned.
- **Mechanical evidence**: zkFuzz mutates the witness-generation program and searches for an input where the mutated trace still satisfies the constraints (a TCCT violation) — a saved `*_counterexample.json` is mechanical proof. Manually: instantiate the smallest parameterization and enumerate witnesses by hand.
- **Anti-pattern**: rare legitimate cases where constraints are intentionally looser than the computation without being exploitable (genuine don't-care output). Require a concrete HARMFUL witness, not just "constraint is weaker than code."
- **Source**: Veridise CCD/WCD detector; zkFuzz (IEEE S&P 2026).

### C11 — Incomplete Fiat-Shamir transcript (Frozen Heart)

- **Signal**: any Rust transcript/challenger usage — `transcript.append_*`/`observe(...)`/`squeeze_challenge`/`sample`/`get_challenge`/zeta/alpha — followed by a challenge/coefficient used in a verification equation.
- **Procedure**: Reconstruct the exact transcript ORDER as a sequence of `(absorb X)` and `(squeeze c)` events. List every value the PROVER sends or freely chooses (commitments, evaluation claims, permutation/cumulative sums, simulated-branch challenges, **public inputs**). For every check "c-weighted combination of values V equals expected," verify each `V ∈ V` was absorbed BEFORE `c` was squeezed. **The set difference (prover-controlled, squeezed-but-not-absorbed) is the vulnerability surface.** Decisive question: can the prover pick `V` AFTER seeing the challenge `c` that `V` should have influenced? The single highest-value omission to check is whether the PUBLIC INPUTS are absorbed before the challenge used to evaluate the public-input / linearization polynomial (zeta in PlonK) — Frozen Heart was exactly this in Dusk/SnarkJS/gnark. Pay special attention to batched/RLC openings and permutation cumulative sums.
- **Mechanical evidence**: reorder check (append precedes squeeze for every prover value); challenge-stability test — mutate one absorbed-claimed value (e.g. a public input) and confirm the derived challenge CHANGES; if it does not, the value was never absorbed. Exploit test — in the prover, defer choosing `V` until after `c` is known, choose `V` to satisfy the final equation, verify. Acceptance = incomplete FS.
- **Anti-pattern**: values that are deterministic functions of already-absorbed data, or that the verifier RECOMPUTES rather than reads from the proof, need not be separately absorbed. A value absorbed under a different wrapper name (public inputs folded into an absorbed PI-polynomial commitment) is bound — trace data flow, not the literal variable. Trace whether the verifier recomputes vs trusts before flagging.
- **Source**: ToB Frozen Heart (Dusk/SnarkJS/gnark, verified); Succinct SP1 security update; zkSecurity Phantom Challenge; Dao et al. "Weak Fiat-Shamir Attacks on Modern Proof Systems" (eprint 2023/691); SP1 GHSA-8m24-3cfx-9fjw.

### C13 — Commitment binding / fold-to-zero (shared binding secret across N commitments)

- **Signal**: a verifier/VK that aggregates N things (commitments, inputs, lookups) into ONE pairing/equation; a loop over commitments that all pair against the SAME `[sigma]2`/`[delta]2`; a custom commitment scheme whose VK has fewer independent G2 points than committed vectors; an unvalidated index map (`chip_ordering`).
- **Procedure**: (1) Identify every aggregate-into-one step. (2) Determine whether the binding element is shared or per-instance. (3) If shared, test the fold-to-zero substitution: can the prover set one component to 0 and absorb its value into another so the AGGREGATE matches but the individual bindings are violated? (gnark CVE-2024-45039: `D_1=0`, `D_2 = D1_correct + D2_correct`.) (4) Check what downstream consumes the individual components — if an in-circuit Fiat-Shamir challenge hashes a component that can be forced to a constant (hash of the zero point), the challenge becomes predictable/non-binding, the real soundness lever. (5) Confirm the fix shape: independent element per instance (k+1 pairings); flag if the code matches the pre-fix single-element shape.
- **Mechanical evidence**: construct two distinct commitment vectors producing the same aggregate (one with a zeroed component, one honest); run the real verifier on both; both accepting = binding is on the sum only = soundness break. Cross-check against the gnark 0.10.0 → 0.11.0 diff.
- **Anti-pattern**: a single shared delta in STANDARD single-commitment Groth16 is correct by design — this class requires N≥2 commitments/inputs that must each be SEPARATELY bound. Do not flag standard Groth16's single delta.
- **Source**: gnark CVE-2024-45039 (verified — single σ reused, fold-to-zero); SP1 `chip_ordering` (Succinct/Zellic).

### C14 — PCS/FRI verifier missing low-degree or query-consistency check (incl. Halo2 query collision)

- **Signal**: a FRI/KZG/multipoint-opening verifier; any circuit that queries the SAME column at two `Rotation`s.
- **Procedure**: Tick the canonical PCS-verifier checklist against the implementation: (1) final folded-poly degree ≤ bound; (2) every folding step mixes a fresh challenge; (3) the `(commitment, eval_point) → value` map detects conflicting values for the same key. For the rotation-collision case, run a BLIND congruence computation (do not pattern-match a constant): for each advice column, enumerate ALL `Rotation` values applied to it; for every pair `(a, b)` compute `a ≡ b (mod 2ᵏ)` where `2ᵏ` is the circuit's domain size (since `ω^(2ᵏ)=1`); ANY congruent pair aliases to the same point, and one evaluation is silently overwritten in the opening map, so a prover edits that witness value to pass the vanishing check.
- **Mechanical evidence**: submit an out-of-degree polynomial / a second conflicting evaluation at a wrapped rotation and confirm acceptance.
- **Anti-pattern**: a higher-level wrapper enforces the degree bound, OR the framework version already includes the collision-detection patch (check the dependency version against the advisory's fixed version). Fixed/preprocessed columns are verifier-fixed, not prover-attackable; only advice columns matter.
- **Source**: zkSecurity Halo2 query-collision (verified — affects Zcash/PSE/Axiom/ezkl); OpenVM FRI GHSA-4w7p-8f9q-f4g2.

### C16 — zkVM operand/state aliasing under-constraint

- **Signal**: a circuit decoding structured input (instruction operands rs1/rs2/rd, opcode selectors, memory addresses) and routing values based on them — RISC-V/EVM/Move VM chips, lookup-driven dispatch, recursion/aggregation verifiers written as circuits.
- **Procedure**: Do NOT start from a memorized RISC-V register list — DERIVE the case matrix from the decoder itself. For every value the decoder routes based on a decoded field, **partition the input space by which decoded fields can be equal** (same source field used twice, source == destination, address collisions, opcode boundary values), then verify a constraint pins the routed value in EACH partition cell. The bug hides in the partition cell that the *uniform witness generator handles correctly* but the *constraint set omits*. For recursion/aggregation verifiers, additionally confirm: a permutation index isn't used to both SET and CHECK a bitmask (no-op); array accesses by a prover-chosen index are bounds-constrained; and a "complete execution" flag is ASSERTED (`assert_complete`), not assumed, in EVERY layer (SP1 `is_complete` was unconstrained in the first layer; zkSync Era's recursion/aggregation gap was the ~$1.9B-surface real instance of this).
- **Mechanical evidence**: differential fuzz (ARGUZZ-style) — run the honest VM and a constraint-only model on the SAME program where two decoded fields alias; if the constraint system accepts a trace the reference VM would not produce, soundness is broken. This is exactly how CVE-2025-52484 was found.
- **Anti-pattern**: don't flag every un-enumerated combination — only partition cells where the routed value is security-relevant and the constraint genuinely differs by case. A lookup keyed on the FULL decoded tuple is sound across all aliasings.
- **Source**: RISC Zero CVE-2025-52484 (verified); SP1/OpenVM recursion advisories; ChainLight zkSync Era; ARGUZZ (arXiv 2509.10819).

### C18 — EC exceptional-case under-constraint (P+P / P+(−P) / equal-x / identity)

- **Signal**: affine EC arithmetic where a slope/λ is computed by a division-shaped hint (`λ <-- num/den`, `cs.assign(λ, num*den.invert())`, an out-of-circuit `num/den`) followed by ONE product constraint `λ·den === num`; denominators of form `(x2−x1)`, `(2·B·y)`, `(y2−y1)`; incomplete-addition formulas; comments like "assumes P≠Q", "incomplete", "assumes nonzero". Halo2: `create_gate` blocks in `ecc/chip/add*`/`mul*` with `(x_p−x_q)` factors; arkworks/bellman affine add helpers assuming distinct x.
- **Procedure**: (1) For each EC op, write the denominator `den` and solve `den==0`: equal points (`x1==x2`), mutually-inverse points (`P==−Q`), `y==0` (order-2 point), and the identity/infinity. (2) Check whether the gadget ADDS a constraint that FORBIDS `den==0` (an `IsZero`/enforce-nonzero, or a completeness branch). The product constraint `λ·den===num` does NOT forbid it — at `den==0` it degenerates to `0===0` and λ (hence the output coords tied only through λ) is FREE. (3) If no forbidding constraint exists, the output is under-constrained at the exceptional input. (4) If the avoidance argument is INDEX-BASED (Halo2's "distinct accumulator indices in −(q−1)/2..(q−1)/2"), verify the index bound holds at every call site and that the ladder switches to COMPLETE addition before the index can reach the collision boundary (Halo2 does this for the last 3 iterations). (5) Trace callers: does any caller feed attacker-influenced points where the exceptional case is reachable (MSM windows, EdDSA R, Pedersen, key aggregation, chained adds that can output O and feed the next)? (6) For an explicit infinity/identity FLAG output, derive the correct "result is O" truth table over `{aIsInfinity, bIsInfinity, x_eq, y_eq}` and compare to the circuit's boolean formula — the classic defect applies the `x_eq && !y_eq → O` branch WITHOUT first requiring both inputs finite (circom-pairing's `(O,−P)` mis-flagged), so gate it on `ab_non0 = (1−aIsInfinity)·(1−bIsInfinity)`.
- **Mechanical evidence**: construct two witnesses for the SAME public input that both satisfy while the output differs (Veridise's circomlib two-λ/two-out counterexamples for `in=0` are the template): Halo2 `MockProver::run(...).verify()==Ok` for both witness_A and witness_B with same instance, different advice → soundness break. arkworks: assign two valid `out` cells for the exceptional point, `cs.is_satisfied()==Ok(true)` for both. For the flag bug, diff against an off-circuit reference (py_ecc/arkworks/sage) over every input class (`O+Q`, `P+O`, `P+(−P)`, `P+P`, `y=0`); circuit says O while reference says −P is the proof.
- **Anti-pattern**: "incomplete addition is used" is by itself NOT a finding — it is correct and intended within its domain. The finding requires showing the domain guard is MISSING or UNSOUND: NOT a bug if (a) a documented index/range argument keeps x distinct, (b) the last iterations use COMPLETE addition (handles all cases), (c) inputs are equality-constrained to sources provably on-curve and ≠ exceptional points, or (d) the infinity branch is correctly gated on both inputs finite. Distinguish a pure COMPLETENESS limitation (honest prover just can't prove the edge — at most liveness/DoS) from a SOUNDNESS break (a degenerate witness with a WRONG output still satisfies). The mechanical discriminator is the two-witness test: `MockProver verify == Ok` on a wrong-output degenerate witness converts suspicion to ground truth.
- **Source**: Veridise circom-bigint/circomlib audit §4.2 (Montgomery add/double, Critical); yi-sun/circom-pairing PR#22 + issue #13 (verified); Halo2 Book "Incomplete and complete addition" + "Variable-base scalar multiplication"; ToB Axiom TOB-AXIOM-13.

### C19 — Point validity: on-curve AND subgroup AND identity, per witnessed point

- **Signal**: a point enters as a witness or public input — decompressed coords, deserialized G1/G2, an aggregated key, an opening-proof commitment, an MSM input. `from_xy_unchecked`, `new_unchecked`, `deserialize_*_unchecked`, `Validate::No`, `read_point`, `decompress`, raw coordinate assignment, or commitments fed to a pairing without a validity gadget. Cofactor>1 curves: BLS12-381 (both Gᵢ), BN254 G2, Baby-Jubjub (h=8), Jubjub.
- **Procedure**: For EVERY point the prover/caller controls, independently answer three questions and find the constraint enforcing each: (a) **ON-CURVE**: is there a constraint `y²==x³+ax+b` (or twisted-Edwards eqn) on the witnessed coords? Decompression that derives y from x is NOT enough if the parity/branch is unconstrained. (b) **SUBGROUP**: is there a prime-order check (`[q]P==O`, or an endomorphism/Bowe-style check)? On-curve does NOT imply prime-order-subgroup membership on cofactor>1 curves. (c) **IDENTITY/INFINITY**: is the identity representable, and handled CONSISTENTLY everywhere it flows (rejected at input vs treated as O in a pairing)? Build the truth table `{on-curve?, in-subgroup?, is-identity?}`, mark which combinations the constraints exclude; any reachable hostile combination is a finding. The identity has multiple encodings (affine "none", projective `z==0`, literal `(0,0)`, all-zero serialization) — a soundness bug arises when ONE module rejects an encoding as invalid while ANOTHER reads the same bytes as the identity and short-circuits a relation (Aztec "0 bug": `e(0,R)=1` holds for all R). Always test the all-zero / `z==0` input end-to-end across decode → on-curve → pairing.
- **Mechanical evidence**: craft a point on-curve but in a small/wrong subgroup (or the identity), feed it as witness/proof element, and assert the proof still verifies / MockProver still satisfies. Verifier-side (Aztec class): submit an all-zero / zero-commitment proof to `verify()`; acceptance = the identity inconsistency. In arkworks, swap `deserialize_*_unchecked` → the validating variant (`Validate::Yes`) and observe the previously-accepted malicious point now fail — that diff localizes the missing check. gnark-crypto ships off-subgroup test points (v0.17.0) as ready adversarial inputs.
- **Anti-pattern**: NOT a bug if the framework's typed constructor enforces on-curve+subgroup at deserialization (`CanonicalDeserialize` with `Validate::Yes`, gnark `IsInSubGroup` called) AND the circuit consumes only those typed values — confirm the UNCHECKED variant is not used. The SUBGROUP leg specifically does not apply on cofactor-1 prime-order curves (BN254 G1, Pallas/Vesta) — but the on-curve and identity legs still do.
- **Source**: 0xPARC zk-bug-tracker (Aztec "0 bug" #7); Nguyen Thoi Minh Quan "The 0 bug"; Sherlock Symbiotic Relay #233 (BN254 G1 subgroup, Jun 2025); Hexens subgroup pitfalls; gnark-crypto v0.17.0 releases.

### C20 — Subgroup-order scalar aliasing (scalar not bound `< l`)

- **Signal**: code computes `[k]G` / `[k]·base` for a base of known prime order l (Baby-Jubjub BASE8; Jubjub; bandersnatch; any cofactor>1 generator), AND k originates from a private input / pubkey-derivation / signature / nullifier-key path. Rust: arkworks `EdwardsVar::scalar_mul_le`/`mul_by_scalar`, bellman/bellpepper `fixed_base_mul`/`EdwardsPoint::mul`, halo2 EC mul, circom-in-Rust `EscalarMul*`. The scalar reaches the gadget via a bit-decomposition (`to_bits_le`, `Num2Bits(N)`, `into_bits_le`) of width N with `2ᴺ > l`.
- **Procedure**: **STEP 1 — Identify the base's true order.** For cofactor>1 generators, read `(p, n, l, h)` from the curve spec; the alias period is the order of the base actually used (subgroup generator → order l; full-group generator → n). Do NOT assume the in-circuit scalar field r equals l — for Baby-Jubjub l ≈ 2²⁵¹ < r ≈ 2²⁵⁴. **STEP 2 — Trace the scalar to its TIGHTEST enforced bound B.** `Num2Bits(N)`/`to_bits_le(N)` only proves `k < 2ᴺ`; `assert k < r` only proves `k < field`. **STEP 3 — Compare B against l.** Bug exists iff `B > l` (two legal witnesses `k` and `k+l` both `< B`). Baby-Jubjub: `Num2Bits(253)` → `B = 2²⁵³ > l` VULNERABLE; `k < r` VULNERABLE; only `k < l` closes it. **STEP 4 — Trace the OUTER use of k:** confirm the app keys/nullifies/indexes on the raw scalar (or hash of it), so `k` and `k+l` map to DIFFERENT outer identifiers but the SAME proven point. **STEP 5 — State the missing constraint:** `k` must be constrained `< l`, not `< 2ᴺ` or `< r`. Cross-check: Ed25519-style "clamping" is NOT a mod-l reduction and does NOT prevent `k` vs `k+l`; confirm any mod-l reduction is CONSTRAINED in-circuit (`<==`), not merely computed in witness gen (`<--`).
- **Mechanical evidence**: deterministic (no fuzzing — the alias is constructive). Generate an honest witness with scalar k; set `k' = k+l`, verify `k'` still under B; re-run with `k'` and show the circuit ACCEPTS it with the IDENTICAL public point. Corroborate the period via host arithmetic: `[l]·BASE == identity` (arkworks `base.into_group().mul_bigint(l).into_affine().is_zero()`). HARM: assert the outer identifier (key hash / nullifier) differs while the proven point is equal.
- **Anti-pattern**: NOT a bug if (1) the scalar is explicitly constrained `< l` (verify the constant is l, not r or 2ᴺ); (2) the OUTER protocol binds on the proven POINT (or a commitment to it) rather than the raw scalar — `k` and `k+l` collapse to one identifier (the primary false-positive guard); (3) the base has prime order == full curve order (cofactor 1); (4) the scalar is purely internal (a blinding factor never exposed as an identifier). Distinguish from the sibling C3 `x` vs `x+r` field-wrap bug: that one is fixed by `< r`; THIS one is not, because `l < r`.
- **Source**: Hexens AvaCloud Baby-Jubjub double-withdrawal (verified, etRapay audit Jan 2025); circomlib `babyjub.circom` `BabyPbk` (verified — `Num2Bits(253)`+`EscalarMulFix`, no `< l`); ERC-2494 (exact `p,n,l,h`); 0xPARC ZkDrops/Nightfall (sibling field-wrap).

### C21 — Groth16 VK / trusted-setup parameter degeneracy

- **Signal**: code embeds or constructs a `VerifyingKey { alpha_g1, beta_g2, gamma_g2, delta_g2, gamma_abc_g1 }` / `PreparedVerifyingKey`, a hardcoded on-chain verifier with literal G1/G2 constants, or a "patched"/hand-edited verifier struct; any verify path whose VK comes from a non-canonical source (deployed constants, embedded JSON, manual field assignment) rather than a vetted setup artifact. Also: setup/keygen code emitting a `ProvingKey`/parameter set whose fields are a SUPERSET of what the verify equation consumes.
- **Procedure**: (1) Trace where each VK field gets its value (setup output? hardcoded literal? deserialized from where?). (2) Treat `gamma_g2` and `delta_g2` as REQUIRED-DISTINCT, REQUIRED-NON-GENERATOR, REQUIRED-NON-IDENTITY: assert `gamma_g2 != delta_g2`, neither `== G2::generator()`, neither `== identity`. If equality cannot be ruled out from the code/constants, that is the finding. (3) For `gamma_abc_g1`/IC: assert no element is the identity, no two are equal/linearly dependent, and `len == num_public_inputs + 1` is enforced somewhere before verify (arkworks `prepare_inputs` `.zip()`s with NO length check — it silently truncates). (4) Reconstruct the verification equation and ask the cancellation question: given the actual VK values, can the attacker pick `A,B,C` (and public inputs) so every pairing term cancels independent of a witness? For `delta2==gamma2` the canonical forgery is `A=alpha, B=beta, C=−vk_x`. (5) If the VK comes from a real ceremony, compute the produced-minus-verified element-set diff: enumerate every group element the setup emits and every element the verify equation reads; any element produced-but-never-verified is the CVE-2019-7167 unused-setup-leak class (a cheating prover folds it into the proof to re-target the statement).
- **Mechanical evidence**: build the actual VK and run the real verifier on a forged proof: arkworks `Groth16::verify_proof(&pvk, &forged_proof, &public_inputs)` with `forged_proof = {a: alpha_g1, b: beta_g2, c: -vk_x}`; returning `Ok(true)` on a statement with NO valid witness is ground truth (FoomClub/VeilCash PoC contracts are the template). VK-independence harness: `assert_ne!(vk.gamma_g2, vk.delta_g2)`, `assert_ne!(vk.delta_g2, G2::generator())`, `for p in &vk.gamma_abc_g1 { assert!(!p.is_zero()) }`, `assert_eq!(vk.gamma_abc_g1.len(), num_inputs+1)`. For the unused-element class, the artifact is the produced-vs-verified set diff plus a citation that the verify equation does not bind the stray element.
- **Anti-pattern**: Groth16 proofs are LEGITIMATELY re-randomizable; a proof that can be re-blinded but still proves the SAME true statement is by-design (snarkjs/arkworks already apply the Gurkan/Novakovic linear-independence fix). Degeneracy requires that verification accepts a FALSE statement (no witness). A VK with distinct random-looking `gamma_g2`/`delta_g2` is fine even if you can't recompute them — only equality/identity/generator collapse is the bug. Toxic-waste secrecy ("someone might have seen tau") is a CEREMONY operational concern, not a code-soundness finding — the reportable class is the structural element-set leak regardless of whether the secret leaked.
- **Source**: dev.to/ohmygod "When ZK Proofs Break" + dev.to/cryip FOOM analysis (`delta2==gamma2`, ~$1.8M); FoomClub-1.6M-PoC / VeilCash-5K-PoC; Zcash CVE-2019-7167 (ECC + Zcash Foundation disclosures); Sui "On the Malleability of Groth16 Proofs"; ark-groth16 `verifier.rs` (read this pass).

### C22 — Unverified prover-supplied evaluations (eval not bound to a commitment)

- **Signal**: a verifier struct named like `ProofEvaluations`/`Proof`/`OpeningProof` with multiple `_eval`/`_at_z` fields; a final pairing/MSM/linearization step (`verify()`, `check_proof()`, `final_pairing()`) that consumes those fields; a SEPARATE opening/aggregation batch (`E_evals`, `commitments_to_open`, `compute_aggregate_witness`).
- **Procedure**: (1) Build `S_used` = every evaluation field read into the final verification equation (grep the struct fields, then each field name's uses inside `verify()`). (2) Build `S_local` = scalars the verifier RECOMPUTES itself from challenges/public inputs (assigned, not read from the proof). (3) Build `S_opened` = scalars in the PCS opening batch (the vector handed to the KZG/IPA opening check). (4) For each member of `S_used`, assert it is in `S_local ∪ S_opened`. ANY field in `S_used` but in neither bucket is the bug: a free variable the prover controls. (5) Cross-check prover/verifier symmetry: every eval the prover writes must be added to BOTH the transcript (FS binding) AND the opening batch (commitment binding) — **transcript-absorption ≠ commitment-binding**; the two are different checks and both are required (dusk-plonk absorbed `q_arith_eval` into the transcript yet omitted it from `E_evals`).
- **Mechanical evidence**: verifier-level malicious-proof mutation — take a real proof, change the target statement so the honest linearization eval differs by δ, set the unbound eval field to `honest_value + δ/coeff` (a single field division), call `verify()`, assert ACCEPT for the false statement. MockProver does NOT catch this (it tests circuit-constraint satisfaction, not the verifier's binding chain) — a verifier-level test (mutate the serialized proof, re-run `Verifier::verify`) is required.
- **Anti-pattern**: an eval that IS absorbed into the transcript but you only checked the transcript — absorption gives grinding-resistance, NOT commitment binding. A value that LOOKS prover-supplied but is recomputed inside `verify()` from the verifier key (`S_local`) is fine — confirm it is assigned, not read from the deserialized proof.
- **Source**: OtterSec dusk-plonk "Unverified Evaluations" (verified — `q_arith_eval`/`q_c_eval`/`q_l_eval`/`q_r_eval` in linearization, absent from `E_evals`; minted 2000 DUSK from zero on testnet); Dusk Network remediation note.

### C23 — Over-constraint / completeness (honest-prover lockout)

- **Signal**: any assigned/intermediate cell bound by a FIXED-WIDTH range gadget, byte/short lookup, k-bit decomposition, or typed Nondet register (`NondetU8Reg`, `range_check::<8>`, an `AssignedValue` forced into `[0,2ᵏ)`); an equality/`enforce`/`===`/custom-gate constraint whose two sides the witness generator computes with a DIFFERENT width or expression; an `assert`/`require` in witness code gating on a range narrower than the protocol's valid-input domain.
- **Procedure**: This is the DUAL of the under-constraint procedure. (1) Recover the SPEC domain for the cell INDEPENDENTLY of the code — from surrounding semantics, what is the full set of honest values it must represent (a RISC-V half-word is 0..65535; a Merkle index is 0..2ᵈᵉᵖᵗʰ−1)? Write it down BEFORE looking at the constraint. (2) Recover the CONSTRAINT domain — what values can actually satisfy the range/width/equality applied (the register bit-width, lookup-table size, decomposition length, modular reduction)? (3) Compute `SPEC \ CONSTRAINT`. If non-empty, name one concrete honest value in the difference (the boundary value just above the constraint's max is the strongest witness — e.g. 256 for an 8-bit reg that must hold 16 bits). (4) For equality/custom gates, trace BOTH sides to their witness-gen source and check identical width/expression. (5) For witness-code asserts, compare the guard against the spec domain. Severity discipline: over-constraint is a LIVENESS/DoS deliverable (honest-prover lockout, griefing), NEVER soundness/counterfeiting — report as completeness/availability (at most High when it breaks a core operation, as with RISC0 `opLH`), never as fund-loss Critical.
- **Mechanical evidence**: INVERT the usual MockProver expectation — assign an HONEST witness containing a boundary value from `SPEC \ CONSTRAINT` and assert `verify().is_ok()`. An `Err(VerifyFailure::ConstraintNotSatisfied)` / `Err(Lookup)` on an HONEST witness IS the over-constraint proof. arkworks: honest assignment → expect `cs.is_satisfied()==Ok(true)`; `Ok(false)` on an honest witness proves it. zkFuzz automates this (Algorithm 1: if P does not crash yet `C(x,z,y)=false` → "Over-Constrained").
- **Anti-pattern**: NOT over-constraint if (a) the spec domain really is that narrow (a genuine boolean cell range-checked to {0,1}); (b) a broader-than-needed intermediate still ACCEPTS every honest trace (multiple valid intermediates is a normal optimization per TCCT Def. 7 — `C` accepting both `(x,z,y)` and `(x,z',y)` is NOT a bug); (c) a redundant/duplicate constraint implied by another (rejects nothing). The discriminator: an over-constraint MUST exclude at least one HONEST trace — if you cannot name a concrete honest value the constraint rejects, downgrade to informational redundancy. Framework discriminator: DEFAULT Circom cannot produce `===`-induced over-constraint (`===` auto-inserts the matching assert, so `T(P) ⊆ S(C)`) — Halo2/arkworks/bellman/plonky2-3 (Argus's targets) CAN, because assignment and constraint are authored as separate statements.
- **Source**: Veridise RISC0 zkVM audit VUL-005 `opLH` (verified, High — `NondetU8Reg` where 16 bits needed); zkFuzz/TCCT Def. 7 + Algorithm 1 (verified via local pdftotext); Veridise WCD detector; Halo2 MockProver as completeness oracle.

### C24 — Noir / Brillig unconstrained-return used without re-constraining

- **Signal**: grep targets that mark the unconstrained→constrained boundary: `unsafe {` blocks, `unconstrained fn` declarations and their call sites, `#[oracle(`/`foreign_call`, `is_unconstrained()`, and any `// Safety:` comment (its presence flags a hand-asserted soundness claim to audit). Each such site returns a witness with NO automatic constraint.
- **Procedure**: (1) Enumerate every unconstrained→constrained crossing. (2) For each returned binding `let v = unsafe { f(...) };`, treat `v` as a FREE witness — assume the prover sets it arbitrarily. (3) Trace every downstream use of `v` in the constrained body and collect the `assert`/equality/range constraints that mention `v` (directly or transitively). (4) Ask whether those constraints UNIQUELY determine `v` from already-constrained inputs — the binding assert must encode the INVERSE check (div: `v*y==x`; sqrt: `v*v==x`; inverse: `v*x==1`; decomposition: `reconstruct(v)==x`; oracle return: a Merkle/state-tree membership proof, not a shape check). (5) If the only constraints are internal-consistency (v compared to OTHER hint outputs, not a trusted input) or weaker than the inverse relation (one-directional `<=`, missing per-limb range check, field-overflow not bounded) → UNDER-CONSTRAINED. (6) For `is_unconstrained()` branches, mentally COMPILE both branches: the compiler statically deletes the dead branch, so analyse only the `else` (constrained) branch and verify the `if`(unconstrained) and `else`(constrained) bodies compute the SAME function — a verify misplaced in the `if` branch is silently dropped.
- **Mechanical evidence**: prove a FALSE statement — supply a witness where the unconstrained/oracle value differs from `f(input)` and show the proof still verifies (Nargo: craft witness, `nargo execute`+`nargo prove`/`nargo verify`, expect PASS on the false witness). Stronger: NAVe (`nargo formal-verify`) — annotate the intended relation with `verify_assert(cond)`; NAVe SMT-encodes the ACIR and asks cvc5 SAT on `program AND NOT cond`; a SAT model assigns the under-constrained witness a divergent value — that model IS the proof.
- **Anti-pattern**: NOT a bug when (a) the value IS fully pinned by a correct inverse/equality assert reachable on EVERY constrained path; (b) the unconstrained value is purely advisory and never flows into a public output or a fund/state/nullifier-gating assert; (c) `is_unconstrained()` branches are provably equivalent and the verify lives in `else`. FALSE-POSITIVE GUARD: do NOT flag every `unsafe` block — only those whose returned witness reaches a constraint-gated decision AND whose binding constraints fail to uniquely determine it. A `// Safety:` comment is NOT evidence of soundness (read its claim, verify the asserts implement it); clean compilation is NOT a soundness signal (the dangling-witness pass catches unused unconstrained values but passes a value bound by a WRONG/weak assert). This is the Noir-vocabulary instance of the same hint/host-assertion hole as gnark `NewHint` (C8/C10) — the procedure transfers; only the grep vocabulary changes.
- **Source**: NAVe "Formally Verifying Noir ZK Programs" (arXiv 2601.09372 — BrilligCall ≡ `true`, 2 vs 379 constraints, `verify_assert`/cvc5); Noir docs (Unconstrained Functions, Oracles explainer "Oracles don't prove anything," `is_unconstrained` branch elimination); noir-lang issue #4442; Nethermind/OpenZeppelin Noir guides.

### C12 / C15 / C17 (brief — methodology pointers)

- **C12 stale-state / recursion-layer ordering**: trace WHEN each validity decision is computed relative to the state it validates; ask if an attacker can drive a referenced slot to default/zero BEFORE the check so it passes/marks-invalid prematurely. Confirm recursion/aggregation completeness flags are constrained in EVERY layer, not just base (SP1 `is_complete`; zkSync Era recursion). PoC: construct the adversarial ordering and verify the wrong effect is accepted. (Source: MACI 0xPARC #10; SP1; ChainLight zkSync Era.)
- **C15 sponge / permutation-chip domain separation + terminal anchoring**: for sponges, check that two different-length inputs cannot reach the same final state — there must be a domain-separated padding scheme (Pad10*, length suffix), not "pad with current state." For permutation Airs, verify the terminal row is anchored (`is_last_block` constant across the block, digest row asserted, partial tails unreachable). PoC: two distinct-length preimages → same digest, or a trace omitting the length suffix / appending past the terminal that still verifies. Anti-pattern: input length fixed and compile-time-known → `PaddingFreeSponge` is fine. (Source: Plonky3 GHSA-3g92-f9ch-qjcm; OpenVM GHSA-9jfx-4f4f-497j.)
- **C17 unused public input**: grep each declared public-input name across constraints; zero hits = candidate (the optimizer may strip the binding). PoC: vary the unconstrained public input and check the proof still verifies. (Source: 0xPARC "Unused Public Inputs Optimized Out.")

## 3. Framework-specific knowledge

Substrate facts generic Rust review misses. Grep targets are bolded — but per §5 and the UCP note in §2, **grep only seeds candidate cells; the binding decision is the forward-determination trace, never the syntactic match.**

**Halo2**
- `region.assign_advice` writes a witness value and creates **NO constraint**. Binding requires `copy_advice` / `constrain_equal` (permutation) OR `assign_advice_from_instance` / `assign_advice_from_constant`. The Orchard root cause. **Grep `assign_advice(` as a copy-vs-constrain CANDIDATE list — then trace whether each cell is later equality-constrained.**
- **Two-call footgun**: `copy_advice`/`constrain_equal` only take effect if `meta.enable_equality(column)` was called for BOTH columns at config time. Missing the enable = the copy is silently inert.
- A custom gate is multiplied by its **selector**; on rows where the selector is 0 the gate imposes nothing. Forgetting `selector.enable(region, offset)` silently disables the constraint for that row — and **MockProver still passes**. Custom gates constrain only RELATIVE (current vs `Rotation::next/prev`) relationships within a region; they do NOT bind a value to an external input unless a copy constraint does.
- **Unassigned advice cells historically default to 0** (zcash/halo2 #614). This hides (a) a forgotten cell that "happens to" satisfy a constraint at 0, and (b) an ungated lookup active on padding rows.
- **EC gadget split**: `mul/incomplete.rs` (the `q_mul` gates) is UNSOUND on its own for the exceptional case and relies on `mul/complete.rs` / `add.rs` to cover P==Q, P==−Q, identity. Var-base scalar mul must switch to COMPLETE addition for the last 3 iterations precisely because incomplete addition's distinct-x guarantee fails once the accumulator index reaches `(q−1)/2`. Auditing only one half misses the contract; the `(0,0)=O` representation is a footgun — any cell witnessable to `(0,0)` without a forbidding constraint opens an exceptional path (C18).
- **Multipoint opening keys evaluations by `(commitment, point)`**; `Rotation(a)` and `Rotation(b)` collide when `a ≡ b (mod 2ᵏ)` — the query-collision bug (C14).
- **`MockProver::verify()` cannot detect a MISSING constraint.** It only checks that EXISTING enabled gates are satisfied against the SUPPLIED witness. A green MockProver on the honest witness is ZERO evidence of soundness. Use it for under-constraint ONLY to confirm a FORGED witness is ACCEPTED; use it for over-constraint (C23) by INVERTING the expectation — feed an HONEST boundary witness and a failure proves over-constraint. Detecting "two satisfying assignments for one public input" requires an SMT/abstract-interpretation analyzer (quantstamp/halo2-analyzer), not MockProver alone.

**Circom**
- `<==` constrains AND assigns; `<--` and `=` ONLY assign; `===` constrains without assigning; `-->` assigns without constraining. **Soundness bugs cluster on `<--`/`=`/`-->` where a `===` companion is missing.** `assert()` is a witness-gen check, NOT a constraint.
- Comparator gadgets (`LessThan`, `BigLessThan`, `IsZero`, `IsEqual`) return an `out` signal that is meaningless unless the caller constrains it (`out === 1`). Instantiation ≠ enforcement (C2). "Unsafe"/efficiency templates deliberately omit internal range/validity checks and rely on the caller — audit the precondition contract at every instantiation (ToB "Tag, you're it: Signal tagging in Circom").
- `Num2Bits(n)` does NOT prove value < 2ⁿ canonically (C3); use `Num2Bits_strict` / `AliasCheck`.
- **DEFAULT Circom cannot produce `===`-induced over-constraint** — every constraint operator also inserts the matching assignment/assert, so `T(P) ⊆ S(C)`. Over-constraint (C23) requires `--constraint_assert_disabled` or a `<--`+`===` divergence. This is why the 0xPARC tracker has essentially no over-constraint entries — and why naive porting from Circom underweights the class for Argus's actual (Halo2/arkworks/bellman) targets.
- **EVM/field boundary**: the SNARK scalar field (~254 bits) < EVM uint256. Values crossing it (nullifiers, group IDs, leaves) must be range-checked `< SNARK_SCALAR_FIELD` (period r); in-circuit `x` and `x+p` are identical, on-chain distinct → double-spend (ZkDrops, Nightfall, Semaphore). The INNER subgroup boundary (period l < r) is a separate, tighter bound (C20).

**Noir / Brillig**
- A Brillig/unconstrained call compiles to a `BrilligCall` ACIR opcode that contributes NO polynomial constraint (NAVe formalises it as the always-true constraint). The return is a FREE witness; the ONLY thing that can bind it is a subsequent `assert` generating an `AssertZero` opcode — and the assert must UNIQUELY determine the value (C24).
- Quantitative tell: the same inverse computed in-circuit vs unconstrained generated 379 vs 2 constraints. A gadget that "feels" like it should emit many constraints but emits almost none is the signature of an unconstrained path never re-constrained.
- Unconstrained calls from constrained code must be wrapped in `unsafe { }` (issue #4442), and the compiler emits a warning unless a `// Safety:` comment is present. `unsafe` does NOT disable constraint generation — it ONLY permits the call. So the boundary is SYNTACTICALLY visible (grep `unsafe`) but there is NO guarantee the return is re-constrained.
- `#[oracle(name)] unconstrained fn` returns are foreign-call witnesses with zero binding ("Oracles don't prove anything. Your Noir program does"). `is_unconstrained()` is a comptime predicate; the compiler statically deletes the dead branch, so constrained-vs-unconstrained paths DIVERGE at compile time — analyse only the surviving branch.
- `Field` wraps mod a 254-bit prime (BN254 base field). A re-constraint assert like `x+y==z` can be satisfied by field-overflow wraparound, so even a PRESENT binding assert is unsound without range checks on the unconstrained limbs (common in `noir-bignum`).

**arkworks (ark-relations / ark-r1cs-std)**
- `new_witness` allocates a prover-private witness (NO relational constraint); `new_input` allocates a public input; `new_constant` is construction-fixed. You must call `enforce_constraint` / `enforce_equal` to bind. Native `.inverse()`/`.invert()` allocated as a witness is the classic under-constraint (RUSTSEC-2021-0075).
- A function named `enforce_*`/`*_gadget` lacking any `enforce_constraint`/`enforce_equal`/`conditional_enforce_equal` in its body computes but does not constrain. `debug_assert!` inside it is NOT a constraint.
- **`CanonicalDeserialize` validation modes**: `deserialize_compressed`/`deserialize_uncompressed` (and `Validate::Yes`) perform BOTH on-curve AND prime-order-subgroup checks; the `*_unchecked` variants (and `Validate::No`) SKIP them. `is_on_curve()` and `is_in_correct_subgroup_assuming_on_curve()` are SEPARATE — on-curve does NOT imply subgroup membership; both are mandatory on cofactor>1 curves (BN254 G2, BLS12-381 both). `AffineVar`/`ProjectiveVar` gadgets and `*_unchecked` constructors do NOT auto-enforce subgroup membership (C19).
- **ark-groth16 `verify_proof`/`prepare_inputs` perform ONLY the IC linear combination and the final pairing equality** — they do NOT subgroup/on-curve-check `proof.a/b/c` or any VK element, and do NOT assert `gamma_abc_g1.len() == public_inputs.len()+1` (`prepare_inputs` `.zip()`s `gamma_abc_g1.skip(1)` and silently truncates). These are DELEGATED to the (de)serialization layer and the caller. Provenance-trace every proof/VK element back to a validating-vs-unchecked deserializer; the gap lives in WHERE the inputs came from, not in `verify_proof` itself (C21/C19). arkworks/SnarkJS implicitly add one R1CS constraint per public input, so NATIVE arkworks verify mitigates the public-input-malleability/range class — the bug lives in hand-written verifiers and on-chain glue.
- Point subgroup checks bound the POINT; scalar range checks bound the SCALAR. They are orthogonal — only the latter fixes `[k]G=[k+q]G` aliasing (C20).
- **`cs.is_satisfied()`** is the in-crate falsification harness: `Ok(true)` on an intentionally-FALSE witness → unsound (under-constraint); `Ok(false)` on an HONEST witness → over-constrained (C23).

**Plonky2 / Plonky3 (STARK; Goldilocks p = 2⁶⁴−2³²+1, BabyBear p = 2³¹−2²⁷+1, Mersenne31 ~31b)**
- `PartialWitness::set_target` / `add_simple_generator` ASSIGN wire values with NO constraint; the constraint side is `builder.connect`, `assert_zero`, `assert_one`, `range_check`, arithmetic gate methods. **Pair every `set_target(`/`add_simple_generator(` against a `connect(`/`assert_`/`range_check(` — as a candidate list, then trace.**
- Small native fields leave little headroom: a decomposition using `NUM_LIMBS × CELL_BITS` of representational space exceeding the target width can field-WRAP (OpenVM AUIPC: 4×8=32 bits > PC_BITS=30 > BabyBear). "Every limb is range-checked" does NOT imply "the value is uniquely represented" — check `max_sum < 2^TARGET_BITS` AND `< p` (C3). Any value used as nullifier/index/key MUST be `< field_order`.
- The idiomatic residual-width trick is to MULTIPLY the top limb by `2^(NUM_LIMBS·CELL_BITS − TARGET_BITS)` before a shared CELL_BITS lookup; a `<<` shift on a field expression (vs a field multiply) or a wrong exponent is a distinct second bug surface on the same line.
- AIR `eval`: any value used as a multiplicative selector or LogUp multiplicity must be asserted boolean (`builder.assert_bool(x)` / `(x)(x−1)=0`); a non-boolean element breaks the multiset argument (OpenVM PhantomAir).
- **FS rule**: every individual evaluation claim AND the permutation cumulative sum must be `observe`d into the challenger BEFORE the binding challenge (zeta / RLC coefficient) is sampled (C11).
- `p3-symmetric PaddingFreeSponge` pads with the CURRENT STATE, not a domain-separated constant → collision-resistant ONLY for fixed compile-time lengths (C15). STARK trace heights are powers of two but permutations run in fixed round blocks → the mismatch creates an unreachable partial "tail" where finalization may be unconstrained; the terminal/digest row must be explicitly anchored.

**Bellman / Bellpepper**
- `cs.alloc(...)` / `AllocatedNum::alloc` allocates a witness via a closure — NO constraint. `cs.enforce(|| ..., |lc| .., |lc| .., |lc| ..)` adds the R1CS `a·b=c`. An `alloc` whose value feeds an output without a matching `enforce` is the canonical hole. Hand-rolled affine adders assuming distinct x are C18 candidates.

**gnark (Go, but in the SNARK ecosystem)**
- `api.NewHint` computes witness values OUTSIDE the constraint system; the hint result MUST be re-constrained in-circuit or it is fully prover-controlled (same hole class as Noir Brillig / arkworks hints). `cs.IsSolved` / the test engine check a witness SATISFIES constraints — they say NOTHING about uniqueness. Export `.r1cs`/`.sr1cs` and run Picus for under-constraint analysis. (gnark ≤0.10.0: Groth16 multi-commitment reused a single σ → fold-to-zero, CVE-2024-45039; fixed 0.11.0 with per-commitment σᵢ.)

**Universal**
- A circuit is a CONSTRAINT SET, not a sequential program — assignment order / data flow implies nothing. Every logical relationship the developer "intends" must appear as an explicit constraint. The auditor's job: enumerate intended relationships and find the constraint for EACH; absence of a constraint = prover freedom = potential forgery.
- The scalar field order r and the curve/base-point order q are NOT always equal: for cofactor>1 and embedded curves (Baby-Jubjub), q ≠ r, so a range check `< r` is insufficient for a scalar driving point multiplication (C20). Conflate neither with the coordinate base field p.
- `debug_assert!` is compiled out in release; `assert!`/`panic!` inside `synthesize`/witness-gen stops the honest prover but not an adversary editing the witness (C8).
- A prover-supplied evaluation absorbed into the FS transcript is NOT thereby bound to a commitment — it must ALSO appear in the PCS opening batch (C22). These are two distinct checks.
- Tool-coverage skew (critical for dispatch): Picus/circomspect/Ecne cover Circom/R1CS (+gnark `.sr1cs` for Picus); Halo2 has only research-grade quantstamp/halo2-analyzer; zkFuzz covers Circom (+Noir WIP) and uniquely flags over-constraint; NAVe (cvc5) covers Noir ACIR; **arkworks/bellman/plonky2-3 have NO off-the-shelf under-constraint detector** — for these the manual UCP + hand-built two-witness PoC (MockProver-forged-witness / `is_satisfied()`) is the primary control.

## 5. Discovery calibration

- **Modal-bug data** (SoK, USENIX Sec 2024): under-constrained → soundness is 95/99 circuit bugs. Optimize the angle for "what binds this value?" above all else (§0).
- **Tool-vs-human**: QED2/PLDI2023 solved 70% (114/163) of circomlib benchmarks, found 13 provably-underconstrained from only 8 distinct templates (the same buggy template recurs even in expert-written code); hard cases were Gröbner-basis timeouts, not detection failures. zkFuzz found 85 bugs incl. 59 zero-days across 452 real Circom circuits with claimed zero false positives. Picus found a real under-constrained SP1 op human audit missed. **A model that systematically enumerates assigned-vs-constrained cells already exceeds the tooling baseline most teams use (5/75 audits used any SNARK tool).**
- **Static linters are weak on the highest-impact class**: the QED2 authors state circomspect "would not be useful for identifying any of the 8 bugs QED2 detected" — it matches only the `<--`-where-`<==`-works syntactic pattern with many false positives. The Orchard bug (assign_advice where copy_advice was needed) is a SEMANTIC binding gap invisible to syntactic linting. **Implication: the LLM must do the forward-trace UCP, not rely on a linter, and must distinguish a true under-constraint from a value fully determined downstream (the `IsZero` `inv` anti-pattern). Treat the §3 grep tables as candidate-seed lists feeding UCP, never as the decision.**
- **Layer-specific recall** (new this pass): the Groth16 VK-degeneracy class (C21) is HIGH-recall for a DIRECTED LLM (the bug lives in a handful of VK constants and one pairing equation; the forgery `A=α,B=β,C=−vk_x` is deterministic) but LOW-recall generic, because the VK constants look like opaque random bytes and the model assumes the setup was correct. The hardest sub-case is PROVENANCE tracing for the subgroup/length trust-boundary gap (C19/C21): the bug is not in `verify_proof` but in WHERE its inputs came from (an unchecked deserializer several modules away) — pure local reading concludes "looks fine." Over-constraint (C23) was found by MANUAL review in the RISC0 audit while sibling under-constraints were found by automated FV — evidence the explicit `SPEC \ CONSTRAINT` procedure adds coverage tools miss.
- **LLM directedness** (Orchard post-mortem, retained in the angle): systematic CHECK-enumeration beats generic prompting (Opus 4.8 generic: 1/4; directed: first run). Feed framework docs (Halo2 book, arkworks README, the curve spec for `p,n,l,h`, the verify equation + VK fields for Groth16) into inventory. Trust mechanical evidence over the "well-audited code" prior (this skepticism failure is the same for Orchard, arkworks, gnark, dusk-plonk). Broader literature (arXiv 2601.19239): LLMs have LOW recall but surface MORE UNIQUE vulns than tools → **use the LLM as a breadth generator feeding mechanical verifiers (Picus / zkFuzz / NAVe / MockProver-forged-witness), not as a standalone oracle.** Pair with a deterministic backend wherever the framework supports one.
- **Effort guidance**: prioritize the mechanical exploit-reproduction step over additional static reasoning — the empirical record shows reasoning-only review is exactly where Orchard, circom-pairing, Tornado MiMC, RISC Zero, dusk-plonk, FOOM, and SP1 all slipped through. Many of the new classes are CONSTRUCTIVE to prove (C20 `k+l`, C21 `C=−vk_x`, C22 a single field division, C18 the two-witness pair), so they convert from `[CODE-TRACE]` to `[POC-PASS]` with minimal setup. These bugs are silent (exploited proofs leave no trace); the audit IS the only line of defense.

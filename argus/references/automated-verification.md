# Stage 3.5 — Automated Verification (Kani + cargo-fuzz)

Stage 3.5 is an OPTIONAL stage between Stage 3 (PoC) and Stage 4 (Adversarial). It operationalizes formal-method tooling for findings where a tool can either prove the bug doesn't exist (drop the finding) or prove the bug does exist (upgrade certainty to 95).

This is a v0.1.10 addition driven by the DeepSeek external review's Item 3.

Read this file at Stage 3.5 start.

## When Stage 3.5 fires

Stage 3.5 runs by default for findings where automated tooling has demonstrated value:

| Trigger condition | Tool to invoke |
|------------------|----------------|
| Math Precision angle owned the finding (V12, V13, V14, V15, V16, V52, V61, V88) | Kani |
| Crypto Soundness angle's threshold/degenerate-input bugs (V61, V62) | Kani |
| Stage 3 ended in `DOWNGRADE(refine)` due to certainty < 80 AND the bug is a math reduction | Kani |
| Stage 3 verdict was Tier 4 written derivation | Kani if math; cargo-fuzz if state-machine; else skip |
| Periphery angle finding involves `unsafe` block (V79, V80) | Miri (UB detector) instead of Kani |
| Execution Trace finding involves multi-tx state machine reachable in pure Rust | cargo-fuzz |

For all other findings, Stage 3.5 is a no-op.

## Pre-flight: tool detection

Extend `scripts/install-deps.sh` with:

```bash
# Kani (Rust model checker)
if ! command -v cargo-kani &>/dev/null; then
  echo "MISSING: cargo-kani (Rust model checker)"
  echo "  Install with: cargo install --locked kani-verifier && cargo kani setup"
fi

# cargo-fuzz (LLVM libFuzzer wrapper for Rust)
if ! command -v cargo-fuzz &>/dev/null; then
  echo "MISSING: cargo-fuzz"
  echo "  Install with: cargo install cargo-fuzz"
fi

# Miri (UB detector)
if ! rustup +nightly component list --installed 2>/dev/null | grep -q miri; then
  echo "MISSING: miri (nightly component)"
  echo "  Install with: rustup +nightly component add miri"
fi
```

Stage 3.5 stops to ask once via `AskUserQuestion`:

> "Argus Stage 3.5 can run Kani / cargo-fuzz / Miri to formally verify or fuzz N findings flagged for automated verification. Tools are user-space installs. How should I proceed?"
>
> - `Install + run` → run install commands above; proceed.
> - `Skip Stage 3.5 entirely` → set `stage-3-5-mode = skip`; flag in Stage 8 mode-warnings.
> - `Run only on already-installed tools` → run Kani-eligible findings if Kani present, etc.; document skipped categories.

## Operations

### A. Kani harness generation

For each Math Precision finding flagged for Kani:

1. **Identify the buggy function**. Read F-NN.md's `location:` field; resolve the cited `pub fn f(args) -> Result<T, E>` signature.

2. **Generate the harness**. Write to `$RUN_DIR/3-5-automated-verification/F-NN/kani-harness.rs`:

```rust
// Auto-generated by Argus Stage 3.5 — do not edit
use <project>::<module>::*;

#[kani::proof]
fn verify_F_NN() {
    // Reconstruct minimal preconditions
    let arg_a: u64 = kani::any();
    let arg_b: u64 = kani::any();
    kani::assume(arg_a > 0);
    kani::assume(arg_b > 0);
    kani::assume(arg_a < 2_u64.pow(40));  // Bound search space; lift if needed.

    // Call the function
    let result = f(arg_a, arg_b);

    // Property to verify (the negation of the bug)
    // For overflow bugs: assert no overflow
    // For wrong-rounding: assert correct direction
    // For threshold off-by-one: assert strict majority semantics
    match result {
        Ok(v) => assert!(/* safety property */),
        Err(_) => {} // error is acceptable
    }
}
```

The orchestrator constructs the harness based on the finding's `bug_class`:

- **overflow**: `kani::any()` for inputs; assert no `checked_*` returns None at any step.
- **wrong-rounding** (V15): two harnesses — one asserts the protocol-favoring direction; one asserts the round-trip.
- **threshold off-by-one** (V61): harness over `n: usize`, asserts `majority_threshold(n) == n/2 + 1` for all `n >= 1`.
- **degenerate-parameter** (V62): harness with `t = 0` constructible; assert NO degenerate-output branch is reachable from public-API entry.

3. **Build + run**:

```bash
cd <project>
cargo kani --harness verify_F_NN --output-format terse
```

Timeout: 5 minutes (configurable via `KANI_TIMEOUT_SECS` env var).

4. **Outcome processing**:

| Kani outcome | Action |
|--------------|--------|
| `VERIFIED` | The property holds for all inputs in the search space. **Drop the finding** (status: `KILL(kani-verified-safe)`). Log search-space bounds in verdict file. |
| `FAILED — Counterexample found` | Kani found inputs that violate the property. **Upgrade certainty to 95.** Counterexample inputs become Tier-1 PoC inputs. |
| `Unknown` (timeout / decision-procedure failure) | No automated verdict. Log and proceed to Stage 4 normally. |
| `Compilation error` (harness wouldn't build) | Log error; proceed to Stage 4 normally. Do not let a buggy harness kill a finding. |

5. **Output**: `$RUN_DIR/3-5-automated-verification/F-NN/kani-output.txt` (full Kani stderr/stdout), `$RUN_DIR/3-5-automated-verification/F-NN/verdict.md` (Argus verdict with cited Kani output).

### B. cargo-fuzz harness

For state-machine / parsing findings:

1. **Set up fuzz directory** (if not present): `cargo fuzz init`.

2. **Generate fuzz target** at `<project>/fuzz/fuzz_targets/F_NN.rs`:

```rust
#![no_main]
use libfuzzer_sys::fuzz_target;
use <project>::<module>::*;

fuzz_target!(|data: &[u8]| {
    if let Ok(input) = SomeInput::deserialize(data) {
        let _ = handler(input);  // we want a crash, not just an error
    }
});
```

3. **Run for 5 minutes**:

```bash
cd <project>
cargo fuzz run F_NN -- -max_total_time=300
```

4. **Outcome processing**:

| Fuzz outcome | Action |
|--------------|--------|
| Crash found (panic / abort / OOM) | **Upgrade certainty to 95.** Crash input becomes Tier-1 PoC input. Save crash to `$RUN_DIR/3-5-automated-verification/F-NN/fuzz-crash.bin`. |
| No crash in 5 minutes | No automated verdict. Log and proceed to Stage 4 normally. (5 minutes is a lower-bound; a longer run may still find crashes.) |
| Setup error (`cargo fuzz init` failed, target wouldn't build) | Log error; proceed to Stage 4. |

### C. Miri (UB detection)

For Periphery findings involving `unsafe` (V79, V80, V85):

1. **Set up Miri**: requires nightly toolchain.
2. **Run the project's existing test suite under Miri**:

```bash
cd <project>
cargo +nightly miri test --package <pkg> --test <relevant_test>
```

3. **Outcome processing**:

| Miri outcome | Action |
|--------------|--------|
| UB reported (unaligned read, OOB, race, etc.) | **Upgrade certainty to 95.** Miri report becomes Tier-1 evidence. |
| All tests pass | No automated verdict. Proceed to Stage 4 normally. (Miri only detects UB on tested paths; absence of UB report ≠ proof of safety.) |

## Stage 0 cost-preview update

`scripts/estimate-cost.py` adds a Stage 3.5 line:

- **Math findings count**: `count(findings flagged Kani-eligible)` × 5 min × Kani-runtime cost (CPU only, no LLM tokens).
- **State-machine findings**: `count(cargo-fuzz-eligible)` × 5 min × CPU.
- **Token cost**: 5k tokens per finding for harness generation (one orchestrator call).

Roughly: a run with 10 Kani-eligible findings adds ~50 minutes wall-clock + 50k tokens. User can opt out at Stage 3.5 entry.

## Stage 4 integration

Findings that come out of Stage 3.5 with:
- `KILL(kani-verified-safe)`: do NOT enter Stage 4. They go directly to Stage 8 `discard.md`.
- `UPGRADE(certainty=95)`: enter Stage 4 normally; Pass A/B/C still run; the certainty boost feeds Pass D as additional evidence (Pass D may UPGRADE severity).
- All other outcomes: enter Stage 4 normally.

## Anti-patterns

- **Don't trust Kani VERIFIED for floating-point math**. Kani's float support is limited.
- **Don't trust cargo-fuzz NO_CRASH as proof of correctness**. 5 minutes is a lower bound; the bug may be reachable at minute 6.
- **Don't generate Kani harnesses with unconstrained `kani::any()` for `Vec<u8>`**. The search space is unbounded; Kani will return Unknown. Always bound length.
- **Don't run Stage 3.5 on findings whose property is "high-level" (e.g., 'attacker drains funds')**. The property must be a low-level safety predicate Kani / a fuzzer can check (no overflow, no UB, no panic, etc.).

## Skip mode

When the user picks `Skip Stage 3.5 entirely`:
- All findings flagged for Stage 3.5 proceed to Stage 4 with their existing certainty.
- Mode warning surfaced in Stage 8: `stage-3-5-skipped: yes`.
- Confidence cap at Stage 8: NO change. Stage 3.5 is opt-in, not a confidence floor.

## Discipline

Stage 3.5 is *additive evidence*, not *replacement for Stage 4*. A Kani VERIFIED still ships under bounded preconditions; Stage 4 may identify out-of-bound inputs. A cargo-fuzz crash is a strong signal but Stage 4 still validates that the crash is an exploitable bug, not just a panic.

The orchestrator MUST verify Kani / fuzz outputs by reading the actual files (counterexamples, crash logs) — do not trust subagent summaries of automated-tool output. The same "code reading wins" principle from X-Ray applies here.
